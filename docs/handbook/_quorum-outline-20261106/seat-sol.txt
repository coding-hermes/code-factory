CORRECTED OUTLINE:

CODE FACTORY OPERATIONS AND SYSTEM SPECIFICATION HANDBOOK

Document rules

  This handbook describes responsibilities, operating paths and interfaces. File-level evidence supports the chapters; it does not determine their arrangement.

  Separate four classifications:
    Requirement: what must hold.
    Design: intended behavior not yet implemented.
    Implementation: behavior established by source or executable evidence.
    Deployment measurement: behavior observed on an identified installation at an identified time.

  Separate document status from system status:
    Document: NOT WRITTEN, DRAFT, REVIEWED, PUBLISHED.
    Evidence: SOURCE-READ, FIXTURE-TESTED, INTEGRATION-TESTED, LIVE-MEASURED, UNVERIFIED.
    Operational result: PASS, FAIL, DEGRADED, REFUSED, UNKNOWN, NOT APPLICABLE, with a reason.

  A rendered diagram is not operational certification.
  A successful request acceptance is not completed work.
  A completed harness process is not an accepted artifact.
  A gate verdict is not a board transition.
  A local merge is not remote publication.
  A backup file is not a demonstrated restoration.

  Use stable module, submodule, contract, procedure, requirement and hazard identifiers.
  Derive inventory totals from the release manifest; do not prescribe counts as a coverage ceiling.
  Preserve M0–M8 as legacy module identifiers and add M9–M15 below.
  Keep evidence appendices and historical verdicts distinguishable from current operating instructions.

PART III — SUBSYSTEM DESCRIPTIONS

  Common chapter fields, applied at the responsibility level:

    A. Purpose, authority and operational position
       Ownership, exclusions, absence/false-report consequences and rationale.

    B. Arrangement and implementation ownership
       Submodules, units, callers, execution location and applicability.

    C. Dependencies and trust
       Runtime/library/service dependencies, versions, custody, networking and absence behavior.

    D. Modes, states and transitions
       Persisted/volatile state, ownership, concurrency and interruption boundaries.

    E. Controls and effective configuration
       Reader, source, precedence, validation, scope, reload/restart and consequence.

    F. Interfaces and data contracts
       Both endpoints, schema, identity, authority and compatibility.

    G. Operating envelope, limits and margins
       Coupled deadlines, leases, capacities, storage limits and boundary behavior.

    H. Normal operating procedures
       Preconditions, numbered actions, expected indications, stop conditions and postconditions.

    I. Contingency and emergency procedures
       Symptoms, discriminator, severity, immediate action, prohibited action and recovery proof.

    J. Indications and observability
       Metrics, logs, stores, correlation, ingestion coverage, freshness and diagnostic interpretation.

    K. Verification and evidence
       Positive/negative checks, exact target, result provenance, retention and falsifier.

    L. Maintenance, change and preservation
       Upgrade, migration, rotation, backup, cleanup and retirement applicability.

    M. Navigation and diagnostic handoff
       Exact upstream/downstream, procedure, contract, hazard and symptom links.

  A field genuinely inapplicable receives a short reason, not invented metrics or generic prose.
  Warning, caution, emergency and informational indications must have defined consequences and actions.
  Submodule procedure details live beneath their owning chapter; the thirteen fields are not copied mechanically for every helper.

CORRECTIONS RANKED: top 10 by damage if ignored

1. Restore the actual runtime architecture to the outline.
   Add scheduler, Crier, fleet dispatcher and inference-relay operating chapters. Without them, a stranger cannot operate or rebuild the specified system even if every mapped script is documented perfectly.

2. Correct dispatch and completion semantics before documenting them as a coherent pipeline.
   Scheduler sends text_b64; the mapped worker requires text. Scheduler treats a correlated reply without ok:false as success; that worker reports failed/refused through status. The fleet dispatcher is a different, compatible-shaped consumer. Name the selected path and test its boundaries.

3. Document credential authority, inference access and guard degradation as operating systems.
   GitHub credentials alone do not describe bus keys, protected recipients, gateway authentication, node inference tokens, upstream credentials or namespace authority. “Guard enabled” is not “message inspected.”

4. Add admission, capacity and target-selection procedures.
   The current outline starts after the scheduler’s controlling decisions. Operators need to distinguish no eligible work, cooldown, budget, capacity, dependency failure and target misconfiguration.

5. Add preservation and recovery procedures for every store and node lifecycle.
   Cover scheduler/Crier state, JSONL and auxiliary files, dispatcher ledger, native sessions, credentials and destructive renewal. A nonempty archive or successful timer is insufficient restore evidence.

6. Correct the unit model’s materially false responsibilities.
   clone_lane.py clones scheduler rows, not repositories. node_identity.py merges JSON, not keys. bunker-crier-connect.sh writes identity/probes, not the bearer. node_freshness.py measures checkout state. reclaim_disk.py has an age gate. These errors would direct repairs to the wrong subsystem.

7. Add coupled limits, custody transitions and crash windows.
   The node worker defaults to a 30-second lease and an 1800-second harness wall, with no renewal path found in that file. Dispatcher jobs, scheduler waits, reply delivery and process descendants have separate bounds. Do not imply exactly-once execution or cancellation from a timeout alone.

8. Separate implemented records from proposed trace and memory architecture.
   Preserve the R1/R2/R3 and run_id designs as requirements with activation prerequisites. Do not render them as existing writers or infer memory coverage from session existence.

9. Make the documentation pipeline capable of delivering this outline.
   The skeleton truncates at 40 entries; the renderer reads absent docs/master; the checker enforces an older eight-heading unit schema rather than these subsystem chapters. Qualify assembly and coverage, not merely prose.

10. Replace generic field compliance with procedures, indications and navigation.
    Keep evidence and failure consequences, merge repetitive introductory/log/evidence headings, and require explicit actions, expected indications, stop conditions, operating margins and next-section links. Reject the “Supporting subsystems” merge.
