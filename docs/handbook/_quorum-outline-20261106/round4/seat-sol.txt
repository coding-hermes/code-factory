CORRECTED OUTLINE:

CODE-FACTORY SYSTEM OPERATIONS AND RECONSTRUCTION HANDBOOK

Document rules

  The handbook describes responsibilities, operating procedures and contracts. File paths are evidence locators, not chapter titles.

  Distinguish:
    DESIGNED — required behavior or a specified interface.
    IMPLEMENTED — source-supported behavior at a named revision.
    DEPLOYED — an installed and activated artifact observed at a named time.
    VERIFIED — the particular claim was exercised against its exact target.
    FAILING — an exercised claim failed.
    UNVERIFIED — evidence is absent, stale, incomplete or inaccessible.
    NOT APPLICABLE — the field does not apply, with a reason.

  Document completeness and system health are independent. A complete chapter may accurately describe a failing subsystem.

  Classify implementations as:
    ACTIVE — production invocation and deployment evidence are named.
    MANUAL — an operator entry point exists; automatic invocation is not established.
    OPTIONAL — a declared feature or alternate operating mode, with its enabling condition.
    LEGACY — a superseded implementation with evidence of the supersession.
    DESIGNED-NOT-BUILT — a requirement exists without an implementation.
    INVOCATION-UNVERIFIED — source exists but its production activation is not established.

  A test reference is not production invocation. Absence from one repository is not proof of absence from installed services or external automation.

  One implementation has one primary ownership assignment. Shared behavior is referenced through a contract rather than duplicated as module membership.

  Every measurable statement carries its revision or observation time. Historical contract states and census totals are not carried forward as current facts.

PART II — OPERATIONAL FLOWS

  Every flow contains:
    Trigger and initiating authority.
    Preconditions and required configuration.
    Actors, execution locations and contracts.
    Numbered steps with expected indications.
    Read/write sets and state transitions.
    Branches, refusals, degraded operation and emergency stops.
    Time budgets, retries, idempotency and concurrency.
    Empty-system and first-run behavior.
    Observable exit, retained evidence and next procedure.
    An as-implemented diagram, with designed-but-missing edges visibly distinct.

  II.1 F1 — Dispatch, execution and settlement
    Trigger: admission hands a lane to a selected execution path.
    Exit: correlated task outcome, delivery state, persistence state and acknowledgement state, or named uncertainty.
    Branches: local command, gateway session, fleet dispatcher and node worker.
    Explicitly document incompatible directive and result dialects, late replies, duplicates, crash windows and cancellation.

  II.2 F2 — Provisioning and certification
    Trigger: an authorized project/node declaration.
    Exit: all required qualification legs verified, or exact failed, skipped and unmeasurable legs.
    Sequence: derive declaration; qualify host; create/reuse agent; stage credentials and identity; apply environment and seed; establish gateway authentication; install node layers; verify.
    CREATED is not CERTIFIED.

  II.3 F3 — Run capture, attribution and retrieval
    Trigger: execution produces progress, result or evidence.
    Exit: expected records can be retrieved through stable identities, or missing capture/join/retention is named.
    Separate node run memory, scheduler replication, dispatcher ledger, node seen cache and session accounting.

  II.4 F4 — Documentation production and qualification
    Trigger: source, configuration, requirements or document schema changes.
    Exit: the intended subsystem handbook is rendered with resolvable references and earned issue-specific status.
    Include census, source extraction, authoring, semantic review, structural checks, rendering and delivered-artifact inspection.

  II.5 F5 — Repository integration and publication
    Trigger: a worker submits a branch, commit and evidence.
    Exit: the exact approved change is verified in the intended published branch, or a refusal is recorded.
    Include clean-tree checks, base compatibility, gate execution, hooks, integration, push, remote readback and evidence-bound board transition.
    A worker commit or merge message is not publication proof.

  II.6 F6 — Preventive maintenance
    Trigger: maintenance schedule, resource threshold or detected drift.
    Exit: resource/freshness state remeasured with retained evidence and named omissions.
    Include caches, aged jobs, checkouts, seed drift, policy drift and artifact retention.

  II.7 F7 — Monitoring and alert delivery
    Trigger: sample, state transition, missing progress or threshold breach.
    Exit: the correct observer receives an attributable signal, or the ingestion/alerting gap is named.
    Include process health versus dependency health, missing samples and alert suppression.

  II.8 F8 — Crash, orphan and restart recovery
    Trigger: interrupted controller, service restart, orphaned process or ambiguous dispatch.
    Exit: work and custody reconciled, with no unidentified surviving execution.
    Include ledger gaps, lease expiry, outstanding jobs, late results, retained process identities and safe redispatch rules.

  II.9 F9 — Dependency degradation
    Trigger: an unavailable, refusing or incompatible dependency.
    Exit: explicitly bounded degraded behavior or named fail-closed refusal.
    Distinguish best-effort visibility publication from required work delivery.
    State which failures can retry and which require configuration or authorization changes.

  II.10 F10 — Retirement and reconstruction
    Trigger: authorized removal or rebuild.
    Exit: execution stopped, custody settled, credentials handled, required state preserved and residue checked; reconstruction returns to F2.
    Do not equate destroying a container with retiring a lane, bus identity or credential.

  II.11 F11 — Scheduling admission and allocation
    Trigger: evaluation, supported wake event or operator action.
    Exit: admitted/reserved execution handoff, or reasoned deferral/refusal.
    Include tasks/cooldown behavior, board eligibility, fairness, resource and budget gates, namespace allocation and operator overrides.

  II.12 F12 — Credential lifecycle
    Trigger: issue, dispatch, refresh, expiry, scope change or compromise.
    Exit: intended authentication and scope verified; obsolete validity explicitly handled.
    Separate GitHub App credentials, installation tokens, Crier bearer/signing identity, gateway credentials, proxy node tokens and memory credentials.

  II.13 F13 — Upgrade, migration and rollback
    Trigger: artifact, configuration, policy or schema change.
    Exit: compatible activated revision verified, or rollback/blocked state recorded.
    Include drain, snapshots, installation, migration, reload/restart, effective-value readback and downgrade constraints.

  II.14 F14 — Observability ingestion
    Trigger: a tick, message, execution phase, model turn or sample.
    Exit: the expected record appears at the destination with correct identity, units and timestamp, or an explicit missing-record outcome.
    Include logs, metrics, scheduler events, session accounting and external replication.

  II.15 F15 — Backup and restoration
    Trigger: schedule, destructive-operation precondition, corruption or drill.
    Exit: required stores restored and checked independently, with unsupported/skipped legs identified.
    Include snapshot consistency, encryption/access, retention, restore order and post-restore operation.

  II.16 F16 — Multi-target execution
    Trigger: an operation names multiple recipients.
    Exit: every intended recipient has a correlated terminal or unresolved outcome.
    Distinguish session fan-out, serial dispatch and any designed-but-unimplemented coordinator.
    Include partial failure, per-target deadlines, cancellation and result aggregation.

  II.17 F17 — TTL renewal and state continuity
    Trigger: expiry threshold or authorized renewal.
    Exit: restored replacement node passes state-continuity and operational checks, or renewal stops safely.
    Include archive verification, destructive renewal, restoration, identity reconciliation and recertification.

  II.18 F18 — Group/template task deployment
    Trigger: deploy a named template to a resolved project group.
    Exit: audited per-project append/skip/error results or the equivalent dry-run plan.
    Include target resolution, idempotency, task identities and partial failure.
    Task deployment does not assert execution completion.

CORRECTIONS RANKED: top 10 by damage if ignored

1. Separate execution paths and result dialects.
   Otherwise the handbook teaches a path that cannot consume its directive or can interpret a failed node result as success. Start with C02–C06 and M2/M9/M11.

2. Correct clone_lane.py’s responsibility.
   It mutates scheduler lane rows. Calling it a repository cloner can lead an operator to alter or disable scheduling while attempting to repair a checkout.

3. Replace inherited contract-health labels with issue-specific evidence.
   Completion-consumer code exists; that does not establish interoperability. Historical “missing,” “works” and “broken” labels must not override current source or substitute for an exercised path.

4. Make credential and identity boundaries operationally explicit.
   node_identity.py does not mint signing keys. Dashboard authentication is not bus membership. Scoped dispatch credentials are not the same mechanism as provisioned token files.

5. Add destructive renewal and multi-store restoration procedures.
   A nonempty archive and an expiry line do not prove restored state. Errors here can destroy the only usable node home or restore only part of the system.

6. Constrain effective configuration and activation.
   The example precedence is partly a target design; installed units and database values can differ from source declarations. Every setting needs its actual reader and readback.

7. Qualify idempotency and crash recovery honestly.
   Completed-result ledgers and seen caches leave execution-before-persistence windows. Do not describe them as exactly-once execution or infer that redispatch is safe.

8. Align the documentation producer, gate, panel and renderer with the new handbook.
   They still select old roots and an eight-heading shape. Without this correction, a valid subsystem outline can still produce or certify the rejected per-file artifact.

9. Give independently operated responsibilities their own addresses.
   Preserve M0/M3/M7/M8 and add the missing foreman, runtime integration, hosting, state/observability and control-plane submodules. Do not hide their recovery authority in “supporting systems.”

10. Reconcile the census and build usable navigation.
    The present outline says 34 submodules while listing 47; the README’s component total also disagrees with the model. Generated, issue-bound registers and procedure cross-references prevent a complete-looking handbook from concealing omitted or stale material.
